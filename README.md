# DreamFund — NEAR HACKATHON / Social Money

A community funding pool where projects receive money in milestones. A milestone is paid only after its evidence is submitted and five eligible NEAR accounts vote. If the community rejects a milestone, the project's **unpaid funds still held by the contract return to the shared pool**.

## Live testnet deployment

- **App:** https://dreamfund-ten.vercel.app/
- **Contract:** [0x_primee.testnet](https://testnet.nearblocks.io/address/0x_primee.testnet)
- **Network:** NEAR testnet
- **Contract source:** `contract/src/lib.rs`

The frontend reads public contract state without a wallet. A testnet wallet is required to create projects, fund the pool, pledge, submit evidence, allocate pool funds, or vote.

## Demo walkthrough

1. Open the app and connect a NEAR **testnet** wallet.
2. Fund the shared pool with `fund_pool()`, or pledge directly to a project with `pledge(project_id)`.
3. Create a project with `create_project(title, goal, milestones)`. Projects support one or two milestones.
4. To use shared-pool money, the contract owner calls `allocate_from_pool(project_id, amount)`. **This allocation action is owner-only in the current demo contract.**
5. The project owner submits a non-empty evidence string with `submit_evidence(project_id, evidence_hash)`. The contract stores the SHA-256 hash generated by the frontend when the input is not already a 32-byte hex hash.
6. Five distinct eligible NEAR accounts vote using `vote_milestone(project_id, approve)`. The project owner cannot vote, and each account can vote once per milestone.
7. When the fifth vote is recorded:
   - **Pass:** a strict majority of approve votes releases the current milestone tranche to the project owner. Reputation increases by one.
   - **Fail:** a strict majority of reject votes marks the project failed and returns its remaining unpaid raised amount to the shared pool.
8. Inspect the contract state and transaction receipts on the NEAR testnet explorer.

## Voting rules and limitations

- The quorum is exactly **five eligible accounts**; resolution happens automatically on the fifth vote.
- A simple majority decides the result. With five votes there can be no tie.
- The project owner is excluded. There is no voting deadline or timeout in this version; fewer than five votes leave the milestone pending.
- One account gets one vote per milestone, but this is **not Sybil-resistant**. One person may control multiple NEAR accounts. This is not a full DAO.
- The app and contract expose the voting flow, but a complete five-account end-to-end vote should be demonstrated with five eligible testnet accounts before describing it as independently verified.
- The pool allocator is the contract owner, not a DAO vote. Direct project pledges are payable and do not require pool allocation.
- Only unpaid funds still held by the contract can be recycled. Funds already transferred to a project owner cannot be clawed back.
- Reputation increments on successful milestone releases; it is not an identity or trust verification system.
- Testnet only. Do not send mainnet funds.

## Contract methods

- `new()` — initializes the contract; an attached deposit seeds the pool.
- `create_project(title, goal, milestones)`
- `fund_pool()` — payable shared-pool contribution.
- `allocate_from_pool(project_id, amount)` — **contract-owner-only** pool allocation.
- `pledge(project_id)` — payable direct project contribution.
- `submit_evidence(project_id, evidence_hash)` — project owner only.
- `vote_milestone(project_id, approve)` — one vote per account per milestone; fifth vote triggers majority resolution.
- `get_milestone_votes(project_id)` — approve/reject/total for the active milestone.
- `get_my_milestone_vote(project_id, voter)`
- `get_pool()`, `get_project(project_id)`, `get_projects()`
- `get_reputation(account)`, `get_owner()`

The contract emits receipt logs for pool funding, pool allocation, votes, milestone payouts, and recycled funds. A transaction receipt is the source of truth for each state transition.

## Deployment and security

The deployment workflow uses repository Actions variables/secrets:
- `NEAR_TESTNET_ACCOUNT_ID` — deployer/contract account.
- `NEAR_TESTNET_PRIVATE_KEY` — full-access testnet key for deployment automation.

Never commit or share the private key or a seed phrase. The public website does not need this deployment key. Use a dedicated testnet account and testnet funds only.
